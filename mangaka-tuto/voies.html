Les deux voies d'exécution

Le moteur fait tourner les tâches longues de deux façons. Le texte (scènes, scénario, direction artistique) et l'export passent par un pool de 4 threads qui travaillent en parallèle. Tout ce qui touche ComfyUI passe par une seule file sérielle : une tâche à la fois, dans l'ordre d'arrivée. Le contrôle qualité y passe aussi, pour que le modèle de vision ne tourne jamais pendant une génération.

Pool JobRunner

Un ThreadPoolExecutor de 4 workers (max_workers=4). Un job en attente peut être annulé ; un job démarré ne s'interrompt pas. Au redémarrage du moteur, les jobs restés « en cours » passent en échec.

engine/mangaka_engine/pipeline/jobs.py

File ComfyUI (SerialJobQueue)

Un seul thread lit la table jobs : les jobs pending de ses étapes, par id croissant (FIFO). La base fait foi : un job ajouté après un autre passe après lui, quelle que soit son étape. Un job en cours peut être interrompu (ComfyUI reçoit l'ordre d'arrêt).

Tout ce qui partage la file ComfyUI

Neuf étapes de job (onze usages, croquis et réparations compris) passent par le même worker. Le moindre essai de référence ou de couverture attend donc la fin des générations lancées avant lui, et inversement.

Ce qui tourne dans le pool

Le reste (créateur de série, identité, brouillons de fiche, lieux, mise en page, lettrage, prompt par fragments) s'exécute pendant la requête HTTP elle-même, sans job. Le paragraphe de prompt rédigé par l'IA, lui, s'écrit dans le job ComfyUI de la case : la file attend le LLM.
